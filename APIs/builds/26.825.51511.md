The local manager reports message start, ordered raw deltas, and final item
completion. React state writes are animation-frame batched, so the adapter must
keep its own accumulator. The host drains queued text before it emits item
completion.

The cloud decoder reports cumulative message snapshots and a conversation-level
`message_stream_complete` update. It does not guarantee append-only message
deltas. A stable message update therefore contains the complete current message.

The native selection positioner reports open and state changes but has no end
callback. It can also update geometry after scroll or resize. The stable adapter
must own selection sessions and must validate that both range ends belong to one
assistant message. This extra ownership hook is required for cloud messages.

All three header owners send their current descriptor list to the same menu adapter.
The header owner evaluates its item builder synchronously. Extension transforms
for this owner must therefore return synchronously. Action callbacks can remain
asynchronous. The native path reports only the selected item ID, so it cannot
prove the input source or modifier keys.

The signed-in ChatGPT sidebar row gives both its direct context menu and hover
`Chat actions` button to the generic menu component. Its `getItems` path is
asynchronous. The stable row identity is `conversation.id`; optimistic state
IDs are not durable thread identity.

### Rich-content exact-build gate

A new exact binding must pass all of these checks before it reports the four
rich-content definition kinds as available:

1. Verify the app version, bundle build, `app.asar` digest, and the five exact
   module identities before the adapter loads. The fifth module pins the
   task-suggestion producer and its null-producer gate.
2. Find exactly one semantic owner shape for the directive map, the
   content-reference dispatcher, the fenced-code component, and each supported
   typed-item dispatcher. A missing or duplicate shape is binding drift.
3. Run adapter contract tests for target matching, predicate mismatch,
   predicate failure, renderer failure, deep immutable JSON snapshots,
   owner-targeted revision and remount, semantic continuity of other owners,
   deterministic disposal, and first-party fallback.
4. Load the compiled `test-fixtures/rich-message-probe/dist` package through
   the public `@chatgptx/api` package in a temporary exact-build profile. Render
   all eight variants across the four definition kinds, use their real UI
   controls, and verify their stored callback records.
5. Run a negative live probe that proves an unregistered directive name and a
   failed directive renderer leave the original directive available. Prove a
   false matcher, a thrown matcher, and a failed renderer on native
   `title_citation`, `text`, local `assistant-message`, and cloud
   `assistant-message` values.

The static owner check and live extension check are both required. A source
anchor alone does not prove that a React owner mounted, and one rendered probe
does not prove that the binding found the intended exact owner.

For this build, use the `scripts/start.mjs run-gate` command in `APIs/README.md`.
The command must succeed before a rebuilt adapter reports these four
definition kinds as available. It performs these stages in order:

1. Exact installed-app, `app.asar`, and rich-content asset verification.
2. Focused verifier, host-source-patch, and renderer-adapter unit tests.
3. Public-API Rich Message Probe type check, build, and contract tests.
4. Temporary live ChatGPT verification with the compiled probe `dist/` package.

The live stage starts ChatGPT directly with
`NODE_OPTIONS=--require runtime/bootstrap.cjs`, which is the production

## Runtime boundary

The current preload does not expose `ipcRenderer`. It exposes a main-world `electronBridge`, and a same-window message can request an AppHost port. The AppHost includes HTTP, browser control, terminals, system permissions, clipboard, files, GitHub, projects, and other app services.

V5 extensions are trusted. They do not need a permission broker. A main extension entry runs in the Electron main process and receives the actual Electron module, Node built-ins, and the host-provided `objc-js` module. Its optional renderer entry receives the stable ChatGPT API and an extension-owned data channel to main.

Injection uses `NODE_OPTIONS=--require runtime/bootstrap.cjs`. The main entry
activates after the bootstrap captures Electron and `app.whenReady()` resolves.
There is no second injection mechanism.

Renderer startup waits for the ChatGPT React root before it imports the exact
UI chunks and attaches their owners.

Primary renderer selection uses an exact-build, test-only binding signal. It
requires a connected `main[data-app-shell-main-surface="default"]` that contains
`header[data-pip-obstacle="app-shell-header"]` and
`[data-app-shell-focus-area="main"]`. It does not use visible page text.

The process split is still required. The primary window has `contextIsolation: true` and `nodeIntegration: false`, and Electron objects such as `BrowserWindow` and `WebContents` cannot cross structured-clone IPC. The renderer therefore does not receive a raw Electron proxy.

Raw AppHost services also stay behind the adapter. This is a stability rule, not an authorization rule: their service composition, ownership context, and DTOs are build-specific.

The app server has its own version and feature checks. The current renderer contains a minimum version check at `0.141.0` and a thread-section check at `0.148.0-alpha.7`. Capability negotiation must include the app-server version. The desktop build number is not sufficient.

## Limits

- Static presence does not prove that a feature is available for each account or host.
- Minified symbols and DTO fields can change without changing the product concept.
- The build proves descriptor flows, panel registration, static routes, and
  named component props. Outside the implemented direct slice, ChatGPTX
  contribution attachments are proposed until live tests pass.
- The main route tree and composer utility bar do not have general first-party
  registries. Their extension registries require exact-build owner hooks.
- This build has no first-party generic transcript-item registry and no
  universal menu registry. The `conversation-item` definition attaches to the
  exact typed-item dispatcher and replaces only a matched item. It does not add
  arbitrary transcript insertion. A generic insertion point and an
  assistant-message context-menu point stay unavailable until a specific
  semantic owner and live attachment test exist.
- Full DTO coverage needs adapter fixtures and live tests. The declarations therefore give deep coverage to core conversation and shell services first.
- Full native trust does not make main-process objects serializable. Native calls from renderer UI still cross an extension-owned data channel.
- Direct Electron and Node APIs follow their upstream versions. Stable ChatGPT product APIs remain independent of those vendor types.
- Local response annotations have static evidence, a direct persisted-Codex
  mapping, and the local live proof recorded above. This is not live proof for
  remote or cloud owners. The cloud
  selection action uses another composer flow and stays unavailable until it
  has a stable mapping and live tests.
- A pending local worktree can show its header menu before a durable thread ID exists. The menu context must represent this state explicitly.
